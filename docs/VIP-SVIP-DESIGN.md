# VIP / SVIP 权益与发放设计（草案）

> 状态：核心权益已由服主确认；发放周期和少量边界语义仍待确认。本文不代表
> 已经写入 LuckPerms 或投入生产。
>
> 本文依据 Git 历史中的 DeluxeMenus、EssentialsX、Residence、DupePlus、
> EnderChestVault 与 TChat 配置重建。历史 LuckPerms 数据库和导出文件均不在
> 仓库中，因此无法证明旧权限节点的完整列表。

## 1. 历史线路

历史上的购买线路是：

1. Srepay 支付成功后在 lobby 执行 `eco give`，按 1 RMB = 1 点券充值。
2. DeluxeMenus 从 lobby 的 EssentialsX 余额扣除 10 或 25 点券。
3. lobby 执行 `lp user <player> parent addtemp vip|svip 31d`。
4. 因三个服务共用 LuckPerms MySQL，临时组自动在 lobby、Velocity 和 2b2t 生效。
5. CommandSync 另外把一次性奖励命令发送到 2b2t：
   - `eco give <player> <amount>`
   - `ecvpages <player> set <pages>`

2026-07-08 删除 Srepay 和 CommandSync 时没有改 DeluxeMenus，线路从该提交起
断裂。MinePay 目前也没有可用于 26.x 的上游构建。

## 2. 建议的组关系

```text
default
  └─ vip
       └─ svip
```

- `svip` 继承 `vip`，不重复维护 VIP 节点。
- VIP 和 SVIP 都是 31 天临时父组。
- 同等级续费使用“累加剩余时间”语义，不能覆盖或缩短现有有效期。
- VIP 与 SVIP 的有效期分别累计、分别到期。购买 SVIP 不转换或消耗已有 VIP
  时间；SVIP 仍通过组继承获得 VIP 权限。
- 权益判定采用最高有效等级优先：S-VIP 生效时覆盖 VIP 的展示、周期金币和签到
  档位，不叠加领取低等级奖励。S-VIP 到期后，如果独立 VIP 时间仍有效，再恢复
  VIP 权益。
- 组权重、前缀和权限均由 bootstrap 管理，禁止只在数据库中手工修改。

## 3. 权益合同

### 3.1 VIP：10 点券 / 31 天

周期权限：

| 权益 | 建议权限/实现 | 状态 |
|---|---|---|
| `/dupe` | `dupeplus.dupe` | DupePlus 当前配置需重新启用权限检查 |
| VIP 聊天组 | `tchat.group.vip` | 历史配置存在 |
| VIP 标签 | `tchat.tag.vip` | 历史配置存在 |
| 自定义渐变称号 | 需要新增受控的称号编辑权限和内容校验 | 历史配置没有完整实现 |
| 死亡后 `/back` | `essentials.back`、`essentials.back.ondeath` | EssentialsX 2.22.0 已确认节点 |
| 7 个、最大 200×200 的领地 | `residence.group.vip` | 必须新增真正的 Residence `vip` 组 |
| 绕过其他领地的 move，可自由出入 | 待 Residence 当前版本实测确认最小权限 | 服主已确认保留；禁止直接授予宽泛的 `residence.admin` |

一次性奖励：

| 权益 | 建议语义 |
|---|---|
| 生存服金币 | 50,000,000；每个成功订单只发一次 |
| EnderChestVault | 至少 1 页；不得把已有 3 页用户降为 1 页 |

周期奖励：

- VIP 生效后每 31 天再发 50,000,000 金币（与首次/月租 VIP 金币量相同）。
- 奖励周期从该次 VIP 有效期的购买/续费线路计算，不按自然月结算。
- 服务器停机错过结算点时，恢复后自动补发；每个 31 天周期最多补发一次。
- S-VIP 生效期间覆盖 VIP 周期奖励，不领取或补发同期的 VIP 50,000,000。
- 历史线路没有实现该定时任务；新实现必须支持累加有效期、防止重复发放并记录
  被高等级覆盖的周期。

### 3.2 SVIP：25 点券 / 31 天

SVIP 继承全部 VIP 周期权限，并增加：

| 权益 | 建议权限/实现 | 状态 |
|---|---|---|
| SVIP 聊天组 | `tchat.group.svip` | 历史配置存在，但显示文本错误地写成 MOD |
| SVIP 标签 | `tchat.tag.svip` | 历史配置缺失，必须新增 |
| 10 个、最大 400×400 的领地 | `residence.group.svip` | 必须新增真正的 Residence `svip` 组 |
| 绕过 move/build/use，可自由出入、破坏和使用 | 待 Residence 当前版本实测确认最小权限 | 服主已确认保留；禁止授予超出这三个 flag 的管理权限 |

一次性奖励：

| 权益 | 建议语义 |
|---|---|
| 生存服金币 | 200,000,000；每个成功订单只发一次 |
| EnderChestVault | 至少 3 页；不得降低已有更高页数 |

周期奖励：

- VIP 每日签到奖励为 1,000 金币；S-VIP 每日签到奖励为 2,000 金币。
- 同一天只按最高有效等级发放一次，不能同时领取 VIP 与 S-VIP 两份签到奖励。

## 4. 到期语义

建议按以下规则实现：

- LuckPerms 临时父组到期后，命令、称号、领地额度和绕过权限立即失效。
- 已创建的 Residence 不自动删除；到期后的编辑、扩建和新建行为按降级后的组限制。
- 金币属于购买时的一次性奖励，不在到期时回收。
- VIP 或 SVIP 到期后进入 60 天 ECV 宽限期；60 天内续费则保留已有页数。
- 宽限期结束仍未续费时回收会员额外 ECV 页数。若另一等级仍有效或仍在宽限期，
  只降到该等级应有的页数，不能直接清零或覆盖更高的有效权益。
- 没有任何有效等级或宽限期时，ECV 页数直接设为 0。服主明确选择直接删除过期
  页及页内物品，不提供迁移或领取；执行前仍需记录审计日志，以便确认是谁、何时
  因何到期被回收。
- 临时组到期不应删除玩家数据文件。

## 5. 前缀与展示

建议由 LuckPerms 元数据作为唯一组前缀来源，TAB 和 TChat 只读取
`%luckperms-prefix%`：

| 组 | 建议显示 |
|---|---|
| VIP | `[VIP]+`，沿用历史绿色样式，并允许受控的自定义渐变称号 |
| SVIP | `[S-VIP]+`，沿用历史彩色样式，并继承 VIP 的自定义称号能力 |

历史 TChat 把 VIP 和 SVIP 的组前缀都写成了 `MOD`，必须修正；历史 tags 配置
只有 VIP，没有 SVIP，也必须补齐。

当前 TChat 只支持配置中预定义的标签，没有玩家自助创建渐变称号的长度限制或
审核流程。自定义称号采用以下业务限制：

- 人工审核后由管理员设置，玩家不能直接写入格式字符串。
- 最多 16 个可见字符；颜色、渐变格式代码不计入可见字符数。
- 禁止冒充管理组、使用控制字符、换行、点击/悬浮事件或不可见文本。
- S-VIP 前缀和样式优先于 VIP；同一时间只展示一个最高等级前缀。

## 6. 发放系统要求

不能恢复为 DeluxeMenus 中无事务的连续 console 命令。新线路至少满足：

1. 每笔购买生成唯一订单 ID。
2. 扣点券、增加临时组、发金币、设置 ECV 页数分别记录状态。
3. 任一步失败可重试，重试不能重复扣款或重复发金币。
4. 组变更直接写共享 LuckPerms；不需要跨服命令同步。
5. 金币和 ECV 必须通过可靠的 2b2t 命令投递队列执行，不能依赖已删除的
   CommandSync，也不能把“消息已发送”当成“命令已成功”。
6. 玩家离线时订单仍应保留，待后端可安全处理时继续执行。
7. 操作必须留下订单、操作者、玩家 UUID、金额、权益、执行结果和时间戳审计。

## 7. 已确认的历史问题

- 旧 SVIP 文案承诺 20,000,000 金币，实际命令只发 5,000,000；新合同已改为
  200,000,000。
- VIP 用户购买或降级操作可能把已有 3 页 ECV 直接覆盖成 1 页。
- Residence 只有 `Default` 和示例 `NextGroup`，从未实现文案中的 VIP/SVIP
  数量和尺寸。
- DupePlus 后续配置升级把 `permission` 改为 `false`，使 `/dupe` 不再是 VIP
  专属。
- TChat 的 VIP/SVIP 都显示为 MOD，且没有 SVIP tag。
- 2026-07-08 删除 CommandSync/Srepay 后，菜单仍调用 `sync` 和 `srepay`。
- 当前 LuckPerms MySQL 只有 `default` 组，没有任何旧 VIP/SVIP 数据可恢复。

## 8. 已确认项

- VIP 不包含 `/home`、`/sethome`；S-VIP 只继承本文列出的 VIP 权益，也不额外
  获得 home 权限。
- VIP 首次奖励 50,000,000 金币，之后每月同额发放。
- S-VIP 首次奖励 200,000,000 金币。
- VIP 保留 move 绕过；S-VIP 保留 move/build/use 绕过。
- VIP 与 S-VIP 均有固定组称号和自定义渐变称号能力。
- VIP/S-VIP 同等级续费累加时间；两种会员时间分别累计，互不转换。
- VIP 的月度金币按每 31 天结算，不按自然月结算。
- 错过结算自动补发；S-VIP 生效时覆盖 VIP 奖励，不重复领取低等级周期奖励。
- VIP 每日签到 1,000，S-VIP 每日签到 2,000；每天只发最高等级的一份。
- 默认玩家没有 `/back`。
- ECV 在会员到期后保留 60 天，宽限期内不续费则降到仍有效的最高等级页数；
  没有其他有效等级时直接设为 0，并删除额外页内物品。
- 自定义渐变称号人工审核，最多 16 个可见字符，格式代码不计长度。
- 点券和金币不更换技术栈：两边都使用 EssentialsX/Vault，但 lobby 余额是点券，
  2b2t 余额是金币，两个服务器的数据目录和余额不互通。

## 9. 实施约束

核心权益参数已经确认。生成 bootstrap 和修改生产配置时，不得自行改变金额、
页数、有效期、覆盖优先级、称号上限或 ECV 回收语义。Residence 的精确最小权限
节点和 ECV 设置为 0 的插件行为仍必须先在测试账号上实测，确认命令不会影响其他
玩家数据，再进入生产。

已在 Paper 26.1.2 与 Leaf 26.2 上逐个实测候选 jar，结果直接影响本合同能否落地：

| 插件 | 结果 | 对权益的影响 |
|---|---|---|
| DupePlus 1.4.3 | 在 Leaf 26.2 启用成功 | `/dupe` 权益可用，权限门槛已恢复 |
| DeluxeMenus 1.14.1 | 在 Paper 26.1.2 启用成功，成功挂接 PlaceholderAPI 与 Vault，载入 13 个菜单 | 购买入口可用，但菜单内容仍需按新合同重写 |
| EnderChestVault 1.0.0 | 在 Leaf 26.2 启用成功，但与历史插件不是同一个 | 没有分页和 `/ecvpages`；见下方决策点 |
| TChat 5.0.0 | 两端均启用失败：启动时下载 SQLite 驱动超时 | 称号与聊天组权益暂不可用；属依赖下载问题，可重试 |
| Residence 6.0.0.1 | 在 Leaf 26.2 启用失败：CMILib 缺 `v1_22_R1` | 领地额度与绕过权益暂不可用，需等上游 |

### 需要重新决策：末影箱权益

历史权益写的是「每页 45 格 × 1 页 / 3 页」，依赖已经无法获取的分页插件。当前可用
的 EnderChestVault 1.0.0 只支持按权限授予单个背包的格数，上限 54 格。

改用它的好处很明显：

- 权益完全由 LuckPerms 权限表达，随临时组自动到期。
- 不需要 `ecvpages set` 跨服命令。
- 不需要 60 天回收任务，也不需要删除玩家物品。

代价是权益形态改变，需要服主确认下列映射（或提出别的数值）：

| 等级 | 建议权限 | 效果 |
|---|---|---|
| default | 无 | 27 格（插件默认） |
| VIP | `ecvault.size.45` | 45 格 |
| S-VIP | `ecvault.size.54` | 54 格（插件上限） |

若坚持保留「3 页」形态，则必须先找到支持 26.x 的分页型末影箱插件，在此之前
S-VIP 的该项权益无法交付。

确认后再生成：

- LuckPerms `default` / `vip` / `svip` bootstrap；
- Residence VIP/SVIP 组；
- TChat/TAB 前缀和标签；
- DupePlus 权限修复；
- 幂等的跨服奖励发放实现；
- 对应的自动化验收脚本。
